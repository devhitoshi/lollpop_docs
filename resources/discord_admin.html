PRINCIPLES

設計の要点

🧵

スレッド＝セッション＝ブランチ

Discord のスレッド1本が、独立した Claude Code のセッション1本と、 git のブランチ1本に対応します。文脈が混ざらず、失敗しても main が汚れません。

🔒

止める場所を4層に分ける

誰が使えるか・何を実行してよいか・何をコミットしてよいか・何を push してよいかを、 それぞれ別のレイヤーで止めます。1つ抜けても残りが効きます。

📦

テキストはリポジトリ、バイナリはドライブ

台本・記事はコミットして URL で辿れるように。動画・音声は Google ドライブに置き、索引だけをリポジトリに残します。

ARCHITECTURE

全体の構成

すべてこの PC の上で動きます。コードもトークンも外部のサービスには渡りません。

USERS 利用者 3名 スマホの Discord。スレッドを立てて話しかける
BRIDGE OpenACP この PC で常駐。スレッドごとにセッションを分け、承認をボタンに変換する
AGENT Claude Code 認証済み。CLAUDE.md とスキルを読んで作業する
OUTPUT リポジトリ／ドライブ 台本・記事は GitHub、動画は Google ドライブ

利用者からは常に「チャットに貼られた本文」と「リンク」だけが見える。GitHub の差分画面も PR 画面も開かせない前提で組んでいる。

なぜ OpenACP が要るのか

Claude Code はターミナルか IDE でしか動かせません。OpenACP はその間に入って、 Discord のスレッドをセッションに割り当て、実行の許可要求をボタンに変え、出力を流し込みます。 自己ホスト型なので、やり取りが第三者のサーバーを経由しません。

SAFETY

止める場所は4層ある

1か所で全部を守ろうとしていません。上の層をすり抜けても、下の層で止まります。

1
OpenACP — 誰が使えるか

利用者の許可リスト

allowedUserIds に入っていないユーザーのメッセージは、 通知もされず黙って捨てられます。3名分の Discord ユーザー ID が入っていることが前提。 空配列だとサーバー全員が使えてしまうので、ここが最重要。

2
Claude Code — 何を実行してよいか

承認ボタン

読み取りと検索は無言で通り、シェルコマンドとファイル書き込みだけが Discord に承認ボタンとして出ます。これは Claude Code の既定の挙動で、設定は入れていません。 リポジトリの .claude/settings.json に制限を書くと、ターミナルから直接使うときにも効いてしまうためです。

3
リポジトリ — 何をコミット・push してよいか

PreToolUse フック（guard_git.py）

force push、main への直接 push、.env・取得済み X 投稿・音源・動画を含むコミット、 git add -f を、実行前に日本語の理由付きで止めます。 その理由文がそのまま Discord に出るので、利用者にも何が起きたか伝わります。 Claude Code のセッション内でしか効かないのが弱点。

4
GitHub — サーバー側の最終防御

ブランチ保護（ルールセット 22720228）

main に対して deletion / non_fast_forward / pull_request を有効化。 バイパス対象を空にしてあるので、admin であるオーナー自身も main に直接 push できません。 手打ちの git や GitHub Desktop からの操作も含めて弾かれます。

3層目と4層目が重なっている理由

フックは早く止まって理由が読めるが、Claude Code を経由しない操作には無力。 ブランチ保護は確実だが、押し戻されるのが push の瞬間で、エラーも英語。 役割が違うので両方かけています。片方を外すならフック側を残すと、日常の手触りは変わりません。

PITFALLS

構築時に踏んだ落とし穴

公式ドキュメントのとおりにやると事故る箇所。パッケージ本体のコードを読んで確認した内容です。

許可リストの置き場が、ドキュメントと違う

ドキュメントは config.json の security ブロックに書けと言うが、 実装はプラグイン設定ファイルを先に読み、そこにあればそちらを使う。 プラグインの初期化がそのファイルを必ず作るので、config.json 側は事実上使われない。

→ plugins\data\@openacp\security\settings.json に書く。書き間違えると全員が使える状態のままになり、エラーも出ない。

許可リストは対話エディタから編集できない

openacp config の Security メニューには「Max concurrent sessions」と 「Session timeout」しかなく、allowed user IDs は表示されるのに項目がない。

→ openacp plugin configure @openacp/security を使う。こちらには「Edit allowed user IDs」がある。

workspace をリポジトリにするとトークンが漏れる

設定は ~/.openacp/ ではなく <workspace>/.openacp/ に作られる。 workspace にリポジトリを指定すると、Bot トークンが平文でリポジトリの中に置かれる。

→ workspace は C:\Users\kawad\work。保険として .openacp/ を .gitignore とフックの禁止パターンの両方に入れてある。

フックの日本語が文字化けしていた

Windows の Python はパイプへ書くとき既定でロケール（cp932）に落ちる。 Claude Code はフックの出力を UTF-8 として読むため、理由文が壊れて届いていた。 構築前から潜んでいた不具合。

→ guard_git.py と after_event_csv.py の両方で sys.stdout.reconfigure(encoding='utf-8') を明示。

できないと分かったこと

OpenACP には「読み取りは自動承認、書き込みは承認要求」のような粒度のある自動承認ルールがありません。 あるのはセッション単位の全承認トグルだけ。ただし Claude Code の既定がまさにその区別をするので、 結果として設定は不要でした。セッション開始時に固定プロンプトを注入する設定も存在しません。 常時読ませたいルールは CLAUDE.md にだけ書けます。

Disable-ScheduledTask -TaskName "OpenACP"

しばらく使わないとき。常時起動を止める

停止したいとき

openacp stop でブリッジが止まります。Discord 側は無反応になるだけで、 スレッドや進行中の内容は消えません。再開は openacp start。

TRIAGE

利用者から「動かない」と言われたら

まったく反応がない（全員）

openacp status → 止まっていれば openacp start。 起動しないなら openacp doctor とログ。 PC の再起動後なら、タスクスケジューラが有効か確認する。

特定の1人だけ反応がない

許可リストにその人の ID が入っていない可能性が高い。仕様上拒否メッセージは出ません。 openacp plugin configure @openacp/security で確認する。

途中で止まったまま進まない

承認ボタンが押されずに放置されている。10分で自動的に拒否されるので、 そのあとは依頼し直しになる。長い作業のときは通知チャンネルも見てもらう。

時間を空けたら話が通じない

セッションのタイムアウト。既定 60 分では短いので延ばしてある。 それでも切れるなら、ブランチ名を伝えて再開してもらう運用に倒す。

ドライブのリンクが開けない

claude-work フォルダがその人の Google アカウントと共有されていない。 リンク共有にはせず、アカウントを個別に追加する。

main を壊されたかもしれない

ブランチ保護が有効なので、履歴の書き換えと直接 push は届いていません。 gh api repos/devhitoshi/lollpop_docs/rules/branches/main で3つのルールが返れば生きています。

トークンが漏れたかもしれないとき

Discord Developer Portal で Reset Token し、 openacp plugin configure @openacp/discord-adapter の「Change bot token」で入れ直して openacp restart。古いトークンはその時点で無効になります。
