# 公式・メンバーアカウントの投稿取得／周囲の反応（エゴサーチ）の取得

`prompts/collect/x_collect.md` が抱えていた2つの仕事をどちらもスクリプト化したもの。

- Grok経由の検索は1クエリ10件で頭打ちになり、期間内の投稿を取りこぼしていた
  （2026-09-01の検証で実測: 30日分のグループ名検索は400件超で、Grokの下限20件を大幅に上回った）
- **エゴサーチ（手順2）も2026-09-01からこのスキルの対象。** 取得自体はtwitterapi.ioの同じエンドポイントで
  可能と分かったため。ただし「ろりぽっぷ」は同名のレンタルサーバーと混同されやすいなど**ノイズ判定に
  文脈判断が要る**点は変わらないので、取得はスクリプトが行い、ノイズ判定は人間かLLMが別途行う
  （下記「周囲の反応（エゴサーチ）の取得」参照）
- twitterapi.ioにアクセスできない環境（信頼モードのClaude Codeリモート環境など）では、
  手順1・手順2とも従来どおり `prompts/collect/x_collect.md` をGrokで実行するフォールバックが使える

## 前提

- `TWITTERAPI_IO_KEY` が環境変数または `.env`（リポジトリルート、`.gitignore` 済み）にあること
- twitterapi.io にアクセスできるネットワーク環境であること（信頼モードのClaude Codeリモート環境では
  403で到達できないことがある。フルアクセス環境では到達を確認済み）
- Python 3（標準ライブラリのみ、追加インストール不要）

## 公式・メンバーアカウントの投稿取得（手順1）

1. **期間を決める。** `until` は終了日の翌日を渡す（`x_collect.md` と同じ慣習。終了日を含めるため）

2. **取得する**

   ```bash
   python3 .claude/skills/x-account-fetch/scripts/fetch_accounts.py \
     --since 2026-08-XX --until 2026-08-YY \
     --max-tweets-per-account 100
   ```

   `--accounts` を省略すると公式＋現メンバー5人が対象になる。元メンバー（卒業済み）を含めたい場合は
   `--accounts lollipop_1116:公式,mana_lpop:愛月まな,...,asaka_lpop:姫杏朝香` のように明示する
   （ハンドルは `prompts/collect/x_collect.md` の「収集対象アカウント」を参照）。

   実行前に推定コストと所要時間を表示し、確認を求める（`--yes` で省略可）。

3. **出力を確認する**

   `work/x_fetch/` に、アカウントごとの生JSON（`<handle>.jsonl`）と、
   `draft_member_posts.md`（日付順・原文そのままのドラフト）ができる。

4. **記事に使う場合**

   `draft_member_posts.md` は原文の全件列挙であり、記事の「メンバーの投稿」節そのものではない。
   `prompts/collect/x_collect.md` の記録ルール（特徴的な一文を選ぶ、要旨は1〜2文、原文の丸写しは避ける）
   に従って、人間かLLMがここから該当する投稿を選び、「ライブ・イベント」「新曲・初披露」
   「アナウンス・告知」「メンバーの投稿」の各節に振り分ける。

## 周囲の反応（エゴサーチ）の取得（手順2）

`prompts/collect/x_collect.md` の「2. 周囲の反応を取得（エゴサーチ）」に対応する、2-1〜2-5のクエリを
`scripts/fetch_egosearch.py` が自動生成して叩く。取得はスクリプトの仕事だが、**採用可否のノイズ判定は
別途、人間かLLM（Claude本体・サブエージェント）が行う必要がある。** グループ名「ろりぽっぷ」は同名の
レンタルサーバー「ロリポップ!」と混同されやすい、「まう」は一般語でもある、などの理由（詳細は
`prompts/collect/x_collect.md` の該当節）でスクリプト単体では判断できない。

```bash
python .claude/skills/x-account-fetch/scripts/fetch_egosearch.py \
  --since 2026-08-25 --until 2026-09-01 \
  --event-terms "夏色ラムネ,クモリニキ,POP CRUSH,バブリー革命" \
  --max-per-query 40
```

- `--event-terms` には対象期間の固有名詞（新曲名・イベント名）をカンマ区切りで渡す。
  `events/data_event.csv` の該当期間の `event` 列から抽出するとよい
- `--max-per-query` は1クエリあたりの取得上限（暴走・課金の歯止め、必須ではないがデフォルト40）
- 実行前にコスト・件数見積りを表示し確認を求める（`--yes` で省略可）
- 結果は下記のローカルキャッシュに保存される。ノイズ判定のために全件を読みたいときは、
  `--out <path>` を渡すとキャッシュを統合・重複除去した1ファイルを書き出す
- ノイズ判定は分量が多い場合（数百件規模）、Explore/general-purposeサブエージェントに
  ファイルの範囲（`offset`/`limit`）を分担させて並列で読ませるとよい（親の文脈を圧迫しないため）

## ローカルキャッシュ

取得した生データ（本文含む）は `x_cache/egosearch/{since}_{until}/{クエリラベル}.jsonl` に
クエリ単位で保存される。**同じ期間・同じクエリは2回目以降キャッシュから読み、APIを叩かない
（課金なし）。** 週刊・月刊まとめは対象期間が重なることが多い（月刊は週刊4本ぶんを含む）ため、
先に週刊で取得したクエリを月刊が流用できる場面がある。

- `x_cache/` はリポジトリ直下、`.gitignore` 対象（`README.md` だけ例外でコミットする）。
  **取得した投稿は他人の著作物のため、本文を含む生データはコミットしない**（後述「規約・法務」参照）。
  `work/`（基本は空にする運用）とは違い、こちらは意図的に永続化する場所
- 古いキャッシュを無視して取り直したいときは `--refresh`（クレジット切れで取得が
  不完全だった場合の再取得などに使う。全クエリを再取得するので `--max-per-query` を
  意図した値にしてから実行すること）
- キャッシュの中身（クエリラベルごとの件数）は毎回の実行末尾に一覧表示される

## 制約・注意点（禁止事項に対応）

- `--max-tweets-per-account` は必須（デフォルトなし）。省略するとエラーで止まる
- 未課金は 0.2 QPS。**逐次のみ・並列化しない**（アカウント間も5秒空ける）
- 429/5xx はジッタ付き指数バックオフでリトライ
- 取得済みJSONLからIDを復元し、再実行時は重複取得しない（中断・再開対応）
- APIキーはコードに書かない。環境変数か `.env` から読む
- **$99/月の自動チャージサブスクリプションに登録しない。クレジットの購入手順を承認なしに実行しない**
- 取得したツイートの生JSON（`work/x_fetch/*.jsonl`、`x_cache/**/*.jsonl`）は `.gitignore` 対象。
  **他人の投稿をコミットしない**

## 既知の癖（2026-09-01の検証で判明）

- **`-from:` 除外オペレーターは信用しない。** 除外指定してもそのアカウント自身の投稿が
  紛れ込むことが実測されている（OR句と併用した場合の挙動と見られる）。
  `fetch_accounts.py` はアカウントごとに個別の `from:` 検索をかけるだけなので、そもそも除外に頼っていない。
  `fetch_egosearch.py` はキーワード検索の性質上 `-from:` 除外に頼らざるを得ないため、
  取得後に著者ハンドルでもう一度フィルタしている（`is_excluded_author`）
- 日付は `since:YYYY-MM-DD until:YYYY-MM-DD`（空白区切り・時刻なし）で動作する。
  ドキュメントが「非対応」と明記しているのはアンダースコア＋時刻つきの `since:..._UTC` 形式で、
  この書き方は対象外
- 単価は `$0.15/1,000ツイート`、`$1=100,000クレジット`、最低課金 `15クレジット/リクエスト`
- 検索エンドポイントは `GET /twitter/tweet/advanced_search`（`docs.twitterapi.io/llms.txt` で確認済み）
- エゴサーチのキーワード検索はアカウント別検索よりノイズ比率が高い。2026-09-01の実測では、
  月刊まとめ用に700件取得して記事に採用できたのは5件（採用率1%未満）だった。
  同名のレンタルサーバー「ロリポップ!」、無関係の別アイドルグループのイベント名との重複、
  ロッテ「爽」アイスと「夏色ラムネ」の表記混同などが主因

## 規約・法務

サードパーティ経由の取得はXの規約との関係がグレー。個人の分析・記事執筆の範囲を前提とする。
収集した投稿は他人の著作物。**再配布・データセット公開・生成モデルの学習利用はしない。**
`x_cache/` は本文を含む生データを永続化するローカルキャッシュだが、この規約があるため
**Gitにはコミットしない**（`.gitignore` 対象）。コミットしてよいのは記事化した引用と出典URLのみ。
