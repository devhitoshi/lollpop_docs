## 2. プラットフォームの制約（2026-09-11 に CLI とドキュメントで確認）

| 項目 | 内容 | 確度 |
|---|---|---|
| 対応フレームワーク | Next.js・Nuxt・静的 HTML（2026-08-27 対応）。React/Vite/Vue/Astro は「予定」 | 事実 |
| Next.js の出力 | `output: 'standalone'` が必須。出力先は `.next/standalone` | 事実（docs） |
| ビルド場所 | **サーバー側**。プロジェクトごとに install / build / output / root の BuildConfig を持ち（`lolipop build-config`）、push か `lolipop deploy` でサーバーがビルドする。パッケージマネージャは npm のみ（pnpm / yarn 不可） | 事実（CLI ヘルプ） |
| Node.js | CLI の要件は **22.12.0 以上**。ローカルは v24.12.0 で足りる。サーバー側は **v22.23.2** で実行されることを確認（後述の実証で `process.version` を出力） | 事実 |
| CLI | `lolipop@2.0.6` を**ローカルに導入済み・ログイン済み**（2026-09-11、ブラウザ認証はオーナーが実施）。`lolipop skill install` で Claude Code 用スキルを入れられる | 事実 |
| サーバー実行 | `sandbox/deploynow-probe/`（SSR ページ＋`/api/hello`）を実際にデプロイし、**SSR・Route Handlers とも正常に動作を確認**（2026-09-11）。実体は AWS Lambda（`*.lambda-url.ap-northeast-1.on.aws`）を CloudFront 経由で配信する構成。ビルドは `npm audit` の CRITICAL/HIGH 警告を出しつつも継続し、デプロイまで通った | **確認済み** |
| GitHub 連携 | GitHub App。**1 プロジェクトにつき 1 リポジトリ**。対象ブランチをダッシュボードで指定、それ以外への push では本番は更新されない。PR プレビュー URL あり | 事実（docs） |
| 環境変数 | ダッシュボードか `lolipop env` で設定。**アップロードした `.env` は読まれない**。本番とプレビューで別管理。1 変数 4,000 バイト、プロジェクト合計 4,096 バイト | 事実（docs） |
| 静的サイト | ルートに `index.html` が無いとルートは 404。`.` 始まりのファイルは非公開。HTML が 1 つも無いとデプロイ失敗 | 事実（docs） |
| 無料プランの枠 | 200 プロジェクト、CPU 4 時間/月、CDN 100 GB/月、独自ドメイン可、商用可 | 事実 |
| DB・KV・cron | 記載なし → **無いものとして設計する**（データはビルド時に JSON 化して同梱、状態はクライアント側） | 事実（記載なし） |
| 画像最適化・Basic 認証・アクセス解析 | 記載なし | 未確認 |

設計への含意: **全ページを静的生成（SSG）にし、CPU 時間を使わない。** サーバー機能に依存しなければ、Cloudflare Pages（9 章）とデプロイナウのどちらにも同じビルド成果物で置ける。OG 画像もビルド時に生成する。

## 5. リスクと守ること

- **歌詞は載せない**（著作権。曲名・披露回数・構成の記述は可）。コール表もオーナー確定前は依存しない。
- **メンバー写真を直貼りしない／「地下アイドル」と書かない／「レア曲」と書かない**（`prompts/write/style_ai_poppar.md`）。写真・音源・イラストは 12 章の許諾が出た範囲だけ。それまでのビジュアルはデザインシステム（`design.md`）のタイポとバンドで作る。
- **他人の投稿の原文を置かない**。ファンの反応を見せるときは X の公式埋め込み（引用の形式）か、件数・要約のみ。
- **非公式であることを全ページに明記**し、運営・メンバーの意図や体調・人間関係の推測を書かない。運営への許諾依頼は制作前・サンプル先行で送る（12 章。法的リスクは [research_2026-09-11_ファン制作物の法的リスク.md](./research_2026-09-11_ファン制作物の法的リスク.md)、その他のリスクとガイドラインの相場は [research_2026-09-11_二次創作ガイドラインの事例とその他のリスク.md](./research_2026-09-11_二次創作ガイドラインの事例とその他のリスク.md)）。
- **名称衝突**（名古屋の同名グループ・仙台の幼稚園）: サイト名・`<title>`・OG に「アイドル」「!!!!!!!」を入れて検索の受け皿にする（`growth_strategy.md` 2.2 の課題への対策を兼ねる）。
- **無料枠の CPU 4 時間/月**: SSG 中心。サーバー処理は OG 画像生成に限り、それもビルド時に寄せる。
- **規約**: 受賞作は一定期間の公開維持が必要。以後も落とさない運用（GitHub 連携で自動デプロイのまま維持）にする。
- **応募フォームの項目が未確認**。9 月分の応募前に一度開いて、作品説明の分量・使用 AI ツール欄の有無を控えておく。

## 7. 9 月作品の仕様: 「!!!!!!! 落ちものパズル」

- 担当カラー 5 色のロリポップが上から落ち、同色 3 つ以上がつながると消える。連鎖でスコア倍率。消すたびに「!」が溜まり、**7 個で「!!!!!!! フィーバー」**（数秒間、消える範囲が広がる）
- 3 分の時間制。終了時に**スコアカード**（スコア・最大連鎖・フィーバー回数・「今日のろりぽっぷ度」）を X 共有
- 結果画面の導線: 「曲を聴く」（`guide/link.md` の配信リンク）、「次の公演」（TimeTree 公開カレンダー）、「ろりぽっぷ!!!!!!! とは」（1 段落＋公式 X）
- **メンバーの似顔絵・音源は運営の許諾（12 章）まで入れない**。サンプル段階の「らしさ」は色・曲名・コール語（うりゃ！おい！／ジャパニーズ）・会場名・ロリポップの形で出し、許諾後に **8bit 風にアレンジ（編曲）した BGM** と 8bit イラストを足す。**編曲は原曲そのままの利用より許諾のハードルが上がる**（12.2 の該当行を参照。音源使用とは別に編曲＝翻案の許諾が要る）
- 応募の説明文の芯: 「一人のファンが、推しの現場の色と言葉だけでゲームを作った」

## 8. リポジトリと構成

- **リポジトリ**: `devhitoshi/lollpop_*`（9 月作品専用、公開）。`lollpop_docs`・`lollpop_video`・`lollpop_data` と同じ命名系。README は本名の名義で、英日併記の短い説明と「非公式のファン制作物」の明記
- **フレームワーク**: Next.js（App Router、TypeScript）。**全ページ静的生成**。`output` は 9 章の切り替え
- **デザイン**: `lollpop_docs/design.md` のトークンを CSS 変数として移植（正は `design.md` のまま。冒頭コメントで転記元を指す。design.md「Iteration Guide 4」の規約）。バンド構成・角丸なし・ピンクは押せるものだけ、を守る。メンバー担当カラーはトークン `mc-kurumi #cc0000 / mc-mayu #f5c400 / mc-mau #7fd4e8 / mc-ami #2e9e5b / mc-mana #ffffff` をそのまま使う（卒業メンバー `mc-asaka` `mc-natsumi` はゲームでは使わない）
- **データ**: `lollpop_docs/events/data_event.csv`・`monthly_setlist_ranking.csv`・`songs/楽曲一覧.md` を `scripts/build_data.py` で `data/*.json` に変換してコミットする（ビルド時に別リポジトリを引かない。更新は Claude Code のスキルで手元から回す）。曲名の名寄せは `setlist-analysis` スキルの正規化を移植する
- **ゲーム**: Canvas＋TypeScript の自前ループ。**外部ゲームエンジンは入れない**（1 画面ゲームには過剰。実装力を見せる意味でも自前の方がよい）。入力はタッチ優先（スマホで遊ぶ人が多い）
- **共有カード**: 1200×630 の PNG。結果画面でクライアント側に Canvas で描いて「画像を保存」「X で共有」。サーバー生成はしない
- **ディレクトリ**: `app/`、`games/puzzle/`（ゲームロジック。React に依存しない純粋な TS）、`data/`（JSON）、`scripts/`（CSV→JSON）、`design/tokens.css`
- **ライセンス**: コードは MIT。データ（公演・曲名）は事実情報。歌詞は含めない。写真・音源・イラストは**運営の許諾（12 章）が得られた範囲だけ**含め、リポジトリには置かず配信側の非公開ストレージに置く

## 9. 公開先の二段構え（Cloudflare Pages → デプロイナウ）

デプロイナウへの公開には `lolipop login`（ブラウザ認証）が要る。これは**完了済み**（2026-09-11）。開発と仮公開は Cloudflare Pages、応募時にデプロイナウへ載せ替える。

| 段階 | 公開先 | 方法 | 注意 |
|---|---|---|---|
| 開発〜仮公開 | Cloudflare Pages | GitHub 連携。`main` への push で自動ビルド・公開。PR ごとのプレビュー URL | Next.js の **SSR は Cloudflare では別アダプタ（OpenNext 等）が要るので使わない**。静的生成のみで組めば、`out/` をそのまま置ける |
| 応募 | ロリポップ！デプロイナウ | GitHub App 連携（1 プロジェクト 1 リポジトリ）。同じリポジトリを接続し、対象ブランチを `main` にする | 応募条件は「デプロイナウで公開した URL」。**応募フォームにはデプロイナウ側の URL を書く**。受賞後も公開維持が要るので、以後の正はデプロイナウ側にする |

両方に同じ成果物を置くために、**サーバー機能（SSR・Route Handlers・DB）に依存しない**設計にする（2 章の含意と同じ）。Next.js の `output` は、デプロイナウ用に `standalone`、Cloudflare 用に `export` を環境変数で切り替える。ページが全部静的なら中身は同じ。

オーナーがやること（残っているもの）:
1. ~~ロリポップ！アカウントの用意~~ 済
2. ~~`lolipop login`~~ **2026-09-11 完了**
3. リポジトリ作成後、デプロイナウのダッシュボードで GitHub App を承認し、対象リポジトリを接続する
4. Cloudflare のアカウントがあれば Pages で同じリポジトリを接続する（無ければ作る。無料）
5. 応募フォームを一度開き、入力項目を控える

## 12. 運営への包括的な許諾依頼

### 12.1 依頼のスタンス

「今回の作品 1 本の断り」ではなく、**今後ろりぽっぷ!!!!!!! を題材にしたネットコンテンツ（ブラウザゲーム・データサイト・縦動画・note 記事）を継続的に作り、コンテストで入賞を目指すので、素材の利用を包括的に認めてほしい**という依頼にする。
使いたい素材は三つ。**楽曲の音源、公式写真、公式写真を元にした 8bit 風イラスト**。これで「ろりぽっぷを全面的に意識した内容」にする。

進め方は**サンプル先行**。許諾前の素材は入れずに（または非公開 URL で）サンプルを作り、「こういうものをやるので使わせてください」と実物で頼む。二次創作一般の可否より、具体物の方が運営は判断しやすい（[research_2026-09-11_二次創作ガイドラインの事例とその他のリスク.md](./research_2026-09-11_二次創作ガイドラインの事例とその他のリスク.md) 示唆）。

**2026-09-11 の方針変更**: 依頼文をいきなり送らず、**2026-09-12 のライブで直接会話して感触を探ってから**、送るかどうか・いつ送るかを判断する。

既に 2026-09-02 に公式写真とメンバー投稿について口頭ベースの OK をもらっている（`data/x/media_permissions.md`）。範囲（使途・改変・クレジット・音源・期限）が未確定で Issue #12 に残っているので、**今回の依頼でその範囲を広げつつ書面（メール・DM の文面）で確定させ、#12 も同時に片付ける**。

### 12.2 法的リスクの要点（出典は [research_2026-09-11_ファン制作物の法的リスク.md](./research_2026-09-11_ファン制作物の法的リスク.md)。法的助言ではなく調査）

| 素材・行為 | 何が問題になるか | 誰の許諾が要るか | 根拠（詳細はメモの節） |
|---|---|---|---|
| 楽曲の音源 | 著作権（作詞・作曲）と**著作隣接権（原盤・実演）は別**。JASRAC は原盤を管理しない。TuneCore Japan で配信していても JASRAC/NexTone 登録とは別 | 原盤は事務所またはレーベル、著作権は作家か管理団体。**曲ごとに J-WID・NexTone で登録の有無を確認**してから聞く | JASRAC 手引き ver.26.3（1 節） |
| 音源をゲームに入れる | JASRAC 管理曲でも「ゲームソフトへの録音」は別手続で、音楽出版社への事前確認が要る。個人の非商用配信は年額の包括契約がある | 同上 | 同 p.9・p.41・p.66（1 節） |
| 音源を X に載せる | **X は JASRAC 包括契約の対象外**（YouTube・TikTok・Instagram は対象）。アプリ内音源で作った動画をアプリ外で使うのも対象外 | 権利者 | JASRAC 契約サービス一覧 2026-08-21（1 節） |
| 公式写真（アー写） | 著作権は撮影者または事務所。FLAP の規約は自社帰属を明記 | 事務所 | FLAP 規約 第 2 条（2 節） |
| 写真→8bit イラスト | 「翻案」に当たるかは江差追分事件の基準。構図・光線・色彩・背景の再現度が低ければ否定例あり（東京地判 H30.3.29）。**手描きで描き起こし、写真の再現度を下げる**方が有利 | 写真の著作権者＋被写体の肖像 | 2 節 |
| メンバーの肖像 | パブリシティ権は「専ら顧客吸引力の利用を目的とする場合」に違法（最判 H24.2.2 ピンク・レディー事件）。補足意見は「写真が主役なら三類型に準ずる」。**肖像を主役にせず、データ・解説の補足に置く**構成が判決に整合 | 本人・事務所 | 3 節 |
| グループ名 | 説明文・タイトルでの記述的使用は商標法 26 条 1 項 6 号の範囲と整理できる余地。**登録の有無は J-PlatPat で未確認** | — | 4 節 |
| AI で写真をイラスト化 | 文化庁「AI と著作権に関する考え方」（R6.3.15）は Image to Image で既存著作物を入力すれば**依拠性を当然に認める**。手描きより不利 | 写真の著作権者＋肖像 | 7 節 |
| コンテスト規約 | 「第三者が権利を保有するものが含まれる場合は、当該権利者から**事前に使用許諾等の承認を得てから応募**」「AI 生成要素も同様」。クレームがあれば主催の損害を**補償するのは応募者**。主催は作品画面を PR に無償使用できる | 依頼文に GMO の PR 使用への同意を含める | 5 節・規約本文 |
| 音源のアレンジ（編曲・8bit 化） | 原曲を編曲する行為自体が、**音源の利用許諾とは別に**著作者人格権（同一性保持権）・翻案権の対象になる。「著作者・著作権者の許可なく編曲・訳詞・替歌など、作品を改変する行為は…著作者人格権および翻案権等の侵害となるおそれ」（JASRAC 手引き p.8）。JASRAC の包括契約は演奏・録音の使用料はカバーするが、**編曲そのものの許諾はカバーしない** | 作詞・作曲者（管理団体は代行しない） | 1 節（JASRAC 手引き p.8） |

### 12.3 法律以外のリスク（出典は [research_2026-09-11_二次創作ガイドラインの事例とその他のリスク.md](./research_2026-09-11_二次創作ガイドラインの事例とその他のリスク.md) B 節）

- **板挟み**: 審査終了（2027 年 1 月中旬）まで作品を削除すると応募無効。受賞後も一定期間の公開維持が要る。運営から途中で取り下げ要請が来ると「削除→無効」か「維持→不履行、またはホスティング側（デプロイナウ規約第 17 条 2 項・Cloudflare）が事前通知なく削除→無効」になる。主催が個別に免除する条項は無い。→ 許諾に**期限**と**取り消し時の猶予（7 日以上）**を入れ、審査期間を先に伝える理由
- **AI 疑惑型の炎上**: VTuber 界で 2025-02、手描きのファンアートに「AI」の疑いが付いただけで作者が誹謗中傷を受け、タレント側が謝罪した（KAI-YOU 2025-02-21）。実際に AI かどうかと独立に対応を迫られる。→ 8bit イラストは**手描きの工程（下絵・ドット打ちの中間画像）を残して見せられる**ようにする
- **運営の体制**: 肖像パブリシティ権擁護監視機構の 2025 年度調査で、侵害事案を把握できた事務所は約 28%、ガイドライン策定は約 52% が「検討中」（PR TIMES 2026-06-25）。小規模事務所に「二次創作ガイドラインを出してほしい」と頼むのは重い。→ **条件案はこちらが書いて、運営は OK/NG と修正だけ返せばよい形**にする
- **主催の PR と無償プラン規約**: コンテスト規約とは別に、デプロイナウ無償プランの規約第 7 条 2 項でも作品が GMO の宣伝に使われ得る。→ 依頼文に明記する
- **黙認は許諾ではない**: 規約は「使用許諾等の承認」を求める。返事が無い状態で素材を入れて応募しない

### 12.8 許諾が得られない場合（出典は [research_2026-09-11_ファン制作物の法的リスク.md](./research_2026-09-11_ファン制作物の法的リスク.md) 示唆）

- AI: 公式写真を Image to Image に入力しない
