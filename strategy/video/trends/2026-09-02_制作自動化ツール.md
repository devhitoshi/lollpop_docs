## 1. 結論（推奨パイプライン）

### 推奨パイプライン（本命）: Remotion + ElevenLabs

| 工程 | ツール | 料金目安 | 手動介入点 |
|---|---|---|---|
| 台本化 | 既存Markdown原稿を人（必要ならLLM補助）でナレーション用の文単位に整形 | 無料 | 事実確認・言い回しの調整は必ず人が行う |
| ナレーション音声 | ElevenLabs API | Starterプラン $6/月〜（30,000クレジット、商用利用可） | 固有名詞の読み間違いチェック |
| 字幕タイムスタンプ | ElevenLabs Forced Alignment（音声合成と同時に単語単位タイムスタンプを取得） | ナレーションと同一課金内 | 誤認識があれば手直し |
| 動画合成・テロップ・図版 | Remotion（React/TypeScript） | 個人・3人以下の組織は無料 | テンプレート（Reactコンポーネント）を最初に1本作るのは人の作業。以降は原稿JSONを流すだけ |
| 書き出し | Remotion CLI（`npx remotion render`）でローカルレンダリング | 無料（自前PCで実行） | なし |
| 投稿 | 当面手動。本数が増えたらBuffer（無料枠3アカウント/月100件） | 無料〜 | キャプション・ハッシュタグの最終確認 |

理由: 依頼者はTypeScript/Reactが書けるため、Reactコンポーネントとして「週刊まとめ」テンプレートを1本作れば、原稿データ（JSON）を差し替えるだけで量産できるRemotionが学習コストと開発効率のバランスに最も優れる。ローカルレンダリングのため何本作っても追加費用がかからず、TTS費用以外はほぼゼロコストで運用できる。ElevenLabsは日本語品質が高く評価されており、かつForced Alignmentで「音声合成と同時に単語単位のタイムスタンプ」が手に入るため、字幕自動化の最大のボトルネック（文字起こし工程）を丸ごと省略できる。

### 代替パイプライン: HyperFrames + VOICEVOX

| 工程 | ツール | 料金目安 | 手動介入点 |
|---|---|---|---|
| 台本化 | 同上 | 無料 | 同上 |
| ナレーション音声 | VOICEVOX（ローカル無料合成） | 無料 | クレジット表記（「VOICEVOX:キャラクター名」）をテロップか概要欄に入れる作業が必須 |
| 字幕タイムスタンプ | VOICEVOXのaudio_query APIが返すモーラ単位の音素長を積算してSRT生成 | 無料 | ロジックは一度作れば自動 |
| 動画合成・テロップ・図版 | HyperFrames（HTML/CSS/JSをNode CLIでMP4化） | 完全無料（Apache 2.0、人数・レンダー回数の上限なし） | HTMLテンプレートの初期作成 |
| 書き出し | `npx hyperframes render` | 無料 | なし |
| 投稿 | 同上 | 同上 | 同上 |

理由: 全工程を無料にできるのが最大の強み（TTSすら無料）。HyperFramesは参考記事が実際に使っていたツールで、「HTML/CSSをエージェントに書かせてCLIでレンダリング」という自動化と相性の良い設計思想を持つ（Node.js製CLI、`npx hyperframes render -c template.html -o out.mp4`という形で動く）。ただし2026年に登場したばかりのOSSで実績・ドキュメントの蓄積がRemotionより薄く、Reactのようなprops型安全の恩恵もない点、VOICEVOXの合成音声は「ナレーター」というより「キャラクターボイス」に寄る点はトレードオフとして留意する。

### 却下した候補（一行理由）

- **Creatomate / JSON2Video / Shotstack**: クラウドAPIで従量課金のため、動画を量産するほどTTS費用と二重に固定費が積み上がる。Node環境構築を避けたい場合の次点候補として保留。
- **FFmpeg直叩き**: 自由度は最大だが、テロップアニメーションや字幕スタイルをfilter_complexでゼロから書くコストが高く、CSSアニメがそのまま使えるRemotionに学習効率で劣る。
- **moviepy（Python）**: 依頼者のPythonは「書けるが専門でない」レベル感であり、テロップ表現力もRemotionのCSSアニメに劣るため優先度を下げた。
- **CapCut**: 公式の外部制御API・CLIが無くGUI手動操作が前提のため、(B)の半自動〜全自動パイプラインには不採用。(A)の手作業ファンカム編集用途では自動字幕・テンプレートが有効なので継続使用を推奨。
- **にじボイス**: 2026年2月4日にサービス終了済みのため選択不可（確認済み）。
- **COEIROINK**: VOICEVOXと同条件（商用可・クレジット必須）だが情報量・実績がVOICEVOXよりやや少なく、無料ローカルTTSの代表としてVOICEVOXを優先。代替候補としては有効。
- **Google Cloud TTS / Azure TTS / OpenAI TTS**: 品質・料金は競争力があるが、ElevenLabsのForced Alignmentほど手軽に「単語単位タイムスタンプ」が取れるか確認しきれず（AzureのWordBoundaryイベントは近い機能を持つが発火が不安定との報告あり、GoogleはSSMLに手動でmarkタグを仕込む必要がある）、字幕自動化の手間で一歩劣ると判断。
- **Windows標準（ナレーター/SAPI）**: 音声保存を前提にしたアクセシビリティ機能ではないため、動画制作用途の主力には不向き。

### 参考記事（note記事）の「AI8割・人2割」構成について

- **転用するもの**: HyperFramesによるHTML/CSSベースの動画組み立て・Node CLIレンダリングという技術選定、ElevenLabsによるナレーション生成とタイムスタンプ取得、「台本→音声→字幕→図版→書き出し」という工程分解の骨格そのもの。
- **捨てるもの**: Higgsfieldなどによるメンバー風AI生成画像・映像の生成工程。依頼者の制約（メンバーのAI生成画像・AI生成音声は使わない）に真っ向から抵触するため全面不採用。画像生成AIを使わない分、素材選定・事実確認は引き続き人が担う必要があり、比率は記事の「8割:2割」よりも人手側に寄ると想定される。無理に比率を再現しようとしないほうがよい。

## 4. 字幕生成の選択肢

TTSナレーションを使う場合とファンカムの生声・環境音を字幕化する場合で最適解が異なる。

### (B) TTSナレーションの場合: TTS自身のタイムスタンプ機能を優先

- **ElevenLabs Forced Alignment**: 音声合成と同時（既存音声+原稿からの事後アラインメントも可能）に文字・単語単位のタイムスタンプを取得できる。字幕焼き込み用SRT生成にそのまま使える。GitHub上には`script-force-alignment`のようなSRT生成ツールも公開されている。
- **VOICEVOX audio_query**: モーラ（音素）ごとのconsonant_length/vowel_lengthを積算することで、アクセント句単位の発話開始・終了時刻をローカルで無料算出できる。個人のZenn記事等に複数の実装例がある。
- **Azure Speech SDKのWordBoundaryイベント**: 単語ごとのAudioOffsetを取得できる公式機能。ただし発火が不安定という報告もある。
- **Google Cloud TTSのSSML `<mark>` timepointing**: 自動ではなく、SSML原稿に`<mark>`タグを自分で挿入した位置についてのみタイムスタンプが返る仕様。単語単位の全自動タイムスタンプではない点に注意。

### (A) ファンカムの生声・環境音を字幕化する場合、または上記TTSタイムスタンプの検証用: ローカルWhisper系

- **faster-whisper**: OpenAI WhisperをCTranslate2で再実装し高速・省メモリ化したもの。ローカル（オフライン）で日本語文字起こしが可能で追加課金なし。データを外部送信しない。
- **whisper.cpp**: C++実装のWhisper。軽量でCPUのみでも動作しやすい。
- **stable-ts**: Whisperの出力に対し単語（トークン）単位までタイムスタンプを安定化させるラッパー。SRT出力にも対応。
- 日本語特化モデル（kotoba-whisper等）も存在するが、汎用モデルより実際の性能が下回る場合があるとの指摘もあり、まず汎用モデルで試すのが無難。

### CapCut自動字幕

CapCutは50以上の言語に対応した自動キャプション機能を持ち日本語にも対応するが、精度は元音声の質に依存し、解説記事でも「自動生成はベース作成であり最終的な手直しが前提」という位置づけ。公式の外部APIがなくGUI操作前提のため、(B)の完全自動パイプラインには組み込みにくい。(A)の手動編集では有力な選択肢。

### 結論

(B)ではTTS自身のタイムスタンプ機能（ElevenLabsのAlignmentまたはVOICEVOXのaudio_query）を第一候補とし、Whisper系はファンカムの生声を字幕化する場合の主力、またはTTSタイムスタンプがずれた場合の検証用と位置づけるのが効率的。

## 5. 楽曲・権利面

本セクションは断定を避け、確認できた範囲とできなかった範囲を明確に分ける。

### 5-1. TuneCore Japan配信曲がTikTok/Instagram/YouTubeの「音源ライブラリ」に載る仕組み

**確認できたこと**

- TuneCore Japanは1度の楽曲登録で、Apple Music・Spotify・TikTok・Instagram/Facebookを含む55以上の配信先・185以上の国と地域へ一括配信するサービスである。
- TuneCore JapanはTikTokへの楽曲配信を2021年に開始。TikTok Music向けには配信手続き開始から最短2日で反映されると案内されている。
- TuneCore Japan公式のTikTok配信ページには、配信された楽曲が「15秒間もしくは60秒間（プレミアム会員のみ）動画のBGMとして利用される」こと、ダッシュボードでBGM利用時の試聴開始位置を30秒単位で指定できること、TikTokの機能により楽曲が早送り・スロー再生などの改変を受けて利用されることがある、という技術的な仕組みが明記されている。
- TuneCore JapanはFacebook/Instagramへの楽曲提供も行っており、Instagramリール等で楽曲を音源として選択できる状態になり得ることが一般論として案内されている。

### 5-2. ファンカムの原盤音声をそのまま投稿した場合の扱い

**確認できたこと**

- TikTokは楽曲ID・音声波形の自動検出システムを持ち、アプリ内の音源ライブラリを経由しない市販曲をBGMとして使うと投稿後に音声がミュートされることがある。
- TikTokは2025年7月25日付でMusic利用規約を改定し、ビジネスアカウント・商用目的（PR案件・アフィリエイト投稿等）の投稿で使用できる楽曲を「商用楽曲ライブラリ（CML）」収録曲に原則制限した。一方、商用目的でない個人の通常投稿についてはこの制限は基本的に適用されないという整理も確認できた。ただしTikTokアカウントを「ビジネスアカウント」に切り替えると「サウンドを追加」の候補がCML内の楽曲のみになるという情報もあり、アカウント種別の切り替え自体が使える音源の範囲に影響する点は運用上の注意点。
- YouTubeはContent IDシステムにより、著作権者が事前に設定したポリシーに従って動画の収益化可否・公開状態が自動判定される。設定次第では「動画は公開されるが広告収益は著作権者に分配される」「一部地域でブロック」「ミュート」など複数のパターンがあり、必ずしも即ミュート・即削除になるわけではない。

**確認できなかったこと**

- 「ろりぽっぷ」楽曲について、実際にYouTube Content IDに音源が登録されているか、TikTokの自動検出データベースにどう登録されているかは権利者側の内部設定次第であり、本調査の情報源（WebSearchとWebFetchのみ、ログイン・アカウント登録なし）では確認できない。実際に投稿してみるまで挙動は確定しないというのが実情に近い。
- ライブ会場で録音した「原盤とは異なる独自録音（フロア収録音）」が、上記の自動検出システムでどう扱われるか（スタジオ音源と同一と判定されるか否か）についての一般的な技術解説は本調査では見つけられなかった。

### 5-3. 一般的に注意すべき点（JASRAC包括契約の範囲、および実演家の権利）

**確認できたこと**

- JASRACなど著作権等管理事業者は、YouTube・TikTok・Instagram等の主要動画投稿サービスと包括的利用許諾契約を締結しており、投稿者は個別許諾を取らずにJASRAC管理楽曲を含む動画を投稿できる。ただしこの包括契約が対象とするのは**作詞・作曲（著作権）のみ**であり、レコード会社等が持つ**原盤権（著作隣接権）は別の権利でJASRACの管理対象外**。原盤（音源そのもの）を利用する場合は原則としてレコード会社等の原盤権者から別途許諾が必要、という整理が複数の解説記事で一致して確認できた。
- さらに本調査で重要と判断した点として、**実演家（歌唱・演奏を行うメンバー本人）は自身の実演を録音・録画されない権利（著作隣接権のうちの録音権・録画権）を専有する**。ライブでの録音・録画は、私的使用目的などの例外を除き、無断で行うと実演家の録音権・録画権を侵害しうる（芸団協CPRAの解説）。つまりファンカムの権利問題は「JASRAC包括契約が作詞作曲しかカバーしない」という論点に加えて、**そもそも撮影・録音行為自体がメンバー・主催者の許諾（＝現場ごとの撮影ルール）を前提にしている**という、より手前の論点がある。
- 地下アイドル現場では、撮影可否・SNS投稿可否のルールがグループやイベントごとに個別に定められているのが一般的（静止画のみ可、動画も可、SNS投稿も可、など段階がある）という実態も確認できた。これは法律の一般論というより現場ごとの運用慣行だが、実務上はこちらの確認が最優先になる。

**確認できなかったこと**

- 「ろりぽっぷ!!!!!!!」自身が公式に定めている撮影・録音・SNS転載のルール（そもそもファンカム撮影が許可されているか、許可されている場合の投稿先制限の有無）は、本タスク（動画制作・自動化ツールの一般調査）の範囲では対象外であり確認していない。**依頼者が所属事務所・グループの公式アナウンスやチケット購入時の注意事項を直接確認する必要がある。**

## 6. 投稿自動化の選択肢

| プラットフォーム | 公式API | 個人アカウントでの利用可否 | 審査の要否 |
|---|---|---|---|
| TikTok | Content Posting API（Direct Post / Upload） | OAuthでの認可自体は個人・法人問わず可能 | 自分でAPIクライアントを作る場合、**審査（audit）に通るまでは投稿が非公開（SELF_ONLY）に強制される**。審査後に公開設定変更が可能になる。個人開発者が自前でこの審査プロセスを通す運用コストは小さくない |
| YouTube | YouTube Data API v3（videos.insert） | 可（OAuth認証） | クォータは1日10,000単位が既定で、動画アップロード1回が1,600単位を消費するため既定のままでも1日数本のアップロードは可能。既定クォータを超える運用をしたい場合は増枠申請が必要で、利用方法を示す動画等の提出を求められ審査に1ヶ月以上かかることもある |
| Instagram | Instagram Graph API（Reels公開） | **個人（Personal）アカウントのままでは不可。Business/Creatorアカウントへの切り替えが必須**、かつFacebookページとの連携が必要 | 自分のアカウントのみに投稿する限定的な用途であればApp Review必須ではないケースもあるが、公開範囲を広げる場合はApp ReviewとBusiness Verification（ビジネス確認）が必要になる |

### 予約投稿ツール（Buffer / Metricool）

- **Buffer**: 無料プランで3アカウントまで接続・月100件投稿まで対応。TikTokは個人アカウントでも自動投稿に対応していると案内されている一方、Instagramの自動投稿にはBusiness/Creatorアカウントが必須で、個人アカウントのままだと投稿時刻に通知が来て手動公開する方式になる、という情報が確認できた。BufferのようなサードパーティはTikTok/Metaの審査を自社で通過済みのAPIパートナーであるため、依頼者が自前でTikTok Content Posting APIの審査を受ける必要がなくなる点が実務上のメリット。
- **Metricool**: 無料プランは1ブランド・月50投稿までで、複数SNSへの本格的なマルチ投稿には有料プランが必要という情報が確認できた。TikTok予約投稿については「リマインダー通知型」（時間になったら通知が来て手動投稿）であり完全自動ではない場合があるとの情報もあり、自動投稿かどうかは契約プラン・仕様を個別に確認する必要がある。

### まとめ

投稿本数が少ないうち（週1〜数本）は手動投稿が最も低コスト・低リスク。本数が増えて自動化したくなった場合は、自前でTikTok Content Posting APIやInstagram Graph APIの審査を受けるより、審査済みのBuffer等を使う方が個人開発者にとって現実的。YouTubeは既定クォータの範囲内であれば個人開発でAPIを自前実装しても運用しやすい。
