## 1. 設計の中心 — 承認をまとめる

毎日 1 本を「候補提示 → 承認 → 台本 → 承認 → 動画 → 確認 → 承認」で回すと、**あなたの承認が毎日 3 回**発生する。
レンダリングは 2〜3 分で終わるので、**律速は機械ではなく承認待ち**。ここを削らないと続かない。

そこで **週 1 回のまとめ作業と、毎日の軽い作業に分ける**。

| いつ | 何をするか | あなたの手間 |
| --- | --- | --- |
| **週 1 回（35〜45 分）** | 候補 10 件から 7 本分（**N3 5 本＋N4 2 本**）の台本＋キャプションを**まとめて承認**し、使う投稿のスクショを 7 枚まとめて撮る（N4 の 2 本はライブ映像の切り出し位置も指定する） | **承認 1 回** |
| **毎日（5〜10 分）** | 在庫から 1 本を動画化 → Drive → スマホで確認 → 投稿 | **確認 1 回** |

**トレンド調査は「在庫のどれを今日出すか」の判断に使う。**
毎日ゼロから選ぶのではなく、承認済みの在庫から today's pick を選ぶ形にすると、
トレンドに合わせやすく、かつ承認待ちで止まらない。

## 3. 各工程の中身

### 工程 1〜2: 取得と抽出

```bash
# lollpop_docs のルートで（週 1）
python3 .claude/skills/x-data-sync/scripts/sync_x_data.py pull

# 候補を出す（既定は直近 60 日 = ストック運用）
cd projects/lollpop_video
python scripts/daily_pick.py                 # 60 日分
python scripts/daily_pick.py --days 7        # 直近だけ見たいとき
python scripts/daily_pick.py --stats         # 供給量の確認
```

- RT・リプライ・本文 60 字未満（挨拶＋自撮り）を機械で落とす
- **`07_台本/used.json` にある投稿 ID は候補から外す**（同じ話を二度使わない）
- **いいね数で並べない。**実データ 458 件で検証したところ、いいね上位は「おはよう＋自撮り」ばかりで、
  既存ファンが顔を見たくて押しているもの。新規への訴求と相関しない

### 工程 3: 選定（4 基準）

`N3_メンバーエピソード.md` の 4 基準を全て満たすものだけ通す。
**実測の通過率は約 5%**（直近 7 日の 41 件中 2 件）。だから直近だけでは足りず、ストック運用が要る。

| # | 基準 | 判定 |
| --- | --- | --- |
| 1 | ギャップがあるか | 「アイドルのイメージ」と「実際の姿」の落差を **1 文で書けるか** |
| 2 | オープンループが作れるか | 「え、どうなったの？」に変換できるか |
| 3 | ペイオフが具体的か | オチを一言・一行動で言い切れるか |
| 4 | 予備知識が要らないか | グループ名・曲名・専門用語なしで通じるか |

### 工程 4: 台本・キャプション

`07_台本/00_台本テンプレート.md` をコピーして `N3-XXX.md` を作る。番号は連番、欠番を再利用しない。
**4 ブロック（フック／状況／展開／ペイオフ）を必ず埋める。**埋まらないものは台本にしない＝工程 3 の判定ミス。

### 工程 5: 一括承認とスクショ ★

あなたがやること:

1. 台本 7 本を読んで、**事実誤認・表現のズレ・出典の間違い**を指摘する
2. 使う投稿を X アプリで開き、**スクショを 1 枚ずつ撮る**（7 枚）
3. スクショを `projects/lollpop_video/assets/screenshots/` に `N3-XXX.png` の名前で置く
4. **N4 の 2 本は、使うライブ映像のファイル名と切り出し位置（開始・終了のタイムコード）を台本に書き込む**

スクショをあなたが撮る理由: **X はログインしないと表示されず、こちらから取得できない**。
ライブ映像の切り出し位置をあなたが決める理由: **どのカットが「決まっている」かは撮った本人にしか分からない**。
ここを機械に選ばせると N4 の一番効く 8 秒が死ぬ。

### 工程 6: トレンドの当たり付け（毎日）

WebSearch で直近のショート動画トレンドを拾い、**在庫 7 本のどれを今日出すか**を 3 行で提案する。

**この工程の限界を先に書いておく。** TikTok・X・YouTube の本体は WebFetch で取得できない（JS 描画・402）。

| 毎日できる | 毎日できない |
| --- | --- |
| トレンド記事・話題の型・流行音源の**言及**を拾う | 個別動画の再生数・尺・冒頭 1 秒・字幕量 |
| 「今日はどの切り口が効きそうか」の当たり付け | TikTok Creative Center の数値（ログイン壁） |

数値の裏取りは月 1 の `06_流行調査手順.md`（手元のブラウザで目視）が担う。**毎日の調査に重い期待をかけない。**

### 工程 7: 音声・動画生成（毎日）

```
台本 → VOICEVOX（audio_query → synthesis）→ WAV ＋ タイミング JSON
     → Remotion（台本 JSON ＋ スクショ ＋ WAV）→ mp4
```

- VOICEVOX は GUI を起動しなくても `vv-engine/run.exe` で API だけ立てられる
- 字幕のタイミングは `audio_query` が返すモーラ長（`consonant_length` / `vowel_length`）を積算して算出する
- 固有名詞は `07_台本/読み辞書.tsv` をユーザー辞書 API に流し込んでから合成する
- **N4 は行ごとに話者 ID を切り替えて合成する。**台本の各行が「どちらの役の台詞か」を持っているので、
  それを話者 ID に写して 1 行ずつ合成し、順に連結する。話者ごとに字幕の色・位置も切り替える
- **N4 はライブ映像の区間だけ現場音を残す。**BGM を下げ、映像の元音声を前に出す（無音にすると現場感が消える）

### 工程 8: 確認と訂正 ★

mp4 を Google ドライブに保存し、あなたがスマホで見る。**スマホで見ることに意味がある**（セーフゾーンは実機でしか判断できない）。

- 保存先: `ろりぽっぷ縦動画/YYYY-MM/N3-XXX/`（mp4・台本・キャプションを同じ場所に）
- 訂正は**台本 JSON を直して再レンダリング**（2〜3 分）。作り直しにはならない
- 見るポイント: 右端 160px・下 400px に文字がかかっていないか／フックで問いが立っているか／オチが分かるか

### 工程 9: 投稿 ★

あなたが手動で TikTok → Instagram → X の順に上げる。

- **TikTok からダウンロードした透かし入りファイルを転載しない**（Instagram は減配する）。元ファイルを各所に上げる
- Instagram（Reels）は締めを「誰かに送りたくなる一行」に差し替える（Meta 公式: シェアが新規リーチに最も効く）
- X は URL を先頭に置きキャプションを短く
- **キャプションに「VOICEVOX:話者名」のクレジットを必ず入れる**（下記 6 章）。**N4 は 2 名分を並べる**

### 工程 10: 計測

投稿 48 時間後と 7 日後に、TikTok アナリティクスから `N3_メンバーエピソード.md` の検証記録へ転記する。
記録するのは 視聴完了率／平均視聴時間／**離脱した秒**／フォロワー外再生比率／プロフィール遷移数、
そして ギャップの型・フックの文言・ペイオフの型。

**3 本ごとに見直す。**

| 離脱の位置 | 疑うところ |
| --- | --- |
| 3 秒に集中 | フックが弱い。問いが立っていない |
| 10 秒前後 | 8 秒ルール違反（絵が変わっていない） |
| 18 秒以降 | ペイオフまで持っている。オチの質だけの問題 |

**N4 は離脱位置の読み方が違う**（ブロック構成が 6 つで秒数がずれる）。`N4_掲示板掛け合い.md` の「離脱した秒の読み方」を使う。
**転記先も型ごとの検証記録に分ける**（混ぜると比較の意味が消える）。

### 工程 11: 6 本ずつ揃ったら 2 型を比較 ★（N4 追加分）

N3・N4 がそれぞれ 6 本たまったら、**中央値で突き合わせる**。

| 見るもの | 判断 |
| --- | --- |
| 視聴完了率の中央値 | 尺が違うので、これだけでは決めない |
| **平均視聴時間（絶対秒数）の中央値** | 「どちらが長く足を止めたか」。N4 が長ければ尺の不利を超えている |
| **N4 の 14 秒前後の離脱** | ここに集中していれば、N3 の「名乗らない」仮説が正しい |
| フォロワー外再生比率 | 新規に届いているか |

**判定後は片方に寄せる。**両方を恒久的に回すのが目的ではない。

## 4. ストックの運用

**候補プールを直近 7 日に限定しない。** 強い候補（「放水ライブ／濡れたあと全身撮るの忘れた」「すっぴんで手売り」）は
8 月の投稿で、時事性がない話は寝かせても使える。既定は 60 日。

| ルール | 内容 |
| --- | --- |
| 使用済みの管理 | `07_台本/used.json` に投稿 ID を記録。二度使わない |
| **在庫の下限** | **承認済み台本が 3 本を切ったら週次作業を前倒しする。**在庫切れで毎日の投稿が止まらないように |
| 時事性のあるネタ | 誕生日・ライブ直後など**期限があるものは優先して消化**する（台本の「消費期限」欄に書く） |
| 寝かせるネタ | 期限がないものは在庫として残し、トレンドに合う日に出す |

## 5. 失敗したときの扱い

| 起きること | どうするか |
| --- | --- |
| スクショが撮れない（投稿が削除・非公開） | **その台本は破棄する。**引用条件「削除・非公開になった投稿は使わない」に従う。在庫から別の 1 本を出す |
| VOICEVOX が起動していない | `vv-engine/run.exe` を起動してから再実行。ポート 50021 の応答で判定する |
| 固有名詞の読み崩れ | `07_台本/読み辞書.tsv` に追記して再合成。**その場しのぎで台本の表記を変えない**（辞書に貯めないと毎回起きる） |
| レンダリング失敗 | 台本 JSON の構文エラーがほとんど。`npx remotion studio` で目視確認してから再実行 |
| 承認が返ってこない日 | **その日は投稿しない。**承認なしで投稿しない（`video-script-needs-approval` の運用） |
| 候補が 4 基準を通らない週 | 期間を 60 日 → 90 日に広げる。それでも足りなければ**その週は本数を減らす**。基準を緩めない |

### N4 は「1 名」ではなく「ペア」を選ぶ（2026-09-04 追加）

N4 は掛け合いなので **2 名を使う**。ここで注意が要るのは、**単体で良かった話者を 1 位から順に 2 人取っても、
ペアとして噛み合うとは限らない**こと。掛け合いが会話に聞こえるかどうかは、声質の良し悪しではなく
**2 人のコントラスト（音の高さ・速度）**で決まる。似た声を 2 つ並べると、話者が代わったことに気づかれず、
掛け合いの効果（注意のリセット）がまるごと消える。

そのため**ペア単位で試聴し直す**。候補 3 名から作れる組み合わせは 3 通り:

| ペア | 備考 |
| --- | --- |
| 春日部つむぎ × 冥鳴ひまり | 両者とも既定の話速で尺に収まる |
| 春日部つむぎ × 九州そら | **九州そらは話速 1.5 倍が必須**（既定 1.0 では N3 の原稿で 34.4 秒かかり、つむぎ・ひまりの 22〜23 秒に対して極端に遅い） |
| 冥鳴ひまり × 九州そら | 同上 |

**役の割り当ても一緒に決める**（どちらが語り役でどちらが合いの手役か）。
合いの手役は 1 行 5〜12 字と短いので、**短い台詞で印象が立つ声**を当てる。

**クレジットは 2 名分をキャプションに並べる。**規約は上表のとおり話者ごとに独立している。

## 8. この文書の前提が崩れる条件

- **通過率 5% が実態と違った場合**（もっと低ければ毎日 1 本は破綻する）→ 週 2〜3 本に落とす
- **承認 30〜40 分が現実的でなかった場合** → 週 7 本を 5 本に減らすか、台本の粒度を粗くする
- **N3 の判定 6 本で採用基準を満たさなかった場合** → 型ごと見直す。このフローは N3 の存続が前提
