# X収集ルートの検証（続き・フルアクセス環境）

前のセッションからの引き継ぎ。**ネットワーク制限のない環境に移したので、今度は実際にAPIを叩ける。**

## まず読むもの

このリポジトリに、経緯と結論と手順が全部置いてある。**推測で動く前にこの3つを読むこと。**

1. `work/x収集ルートの検討.md` — 何を検討して何が争点なのか（**これが判断の土台**）
2. `work/x_ugc_probe.md` — 検証の手順・結果の読み方・未検証な点

補助資料:
- `prompts/collect/x_collect.md`、`prompts/collect/strategy_metrics.md` — 現行の収集ルート（Grok）
- `strategy/metrics_2026-09-01.md` — 現行ルートの実際の出力。**「1クエリ10件の壁」の証拠がここにある**

作業ブランチは `claude/lolipop-review-doenaa`。

## 状況の要約（詳細は上の検討メモ）

- 現行は Playwright + Grok（X Premium 込みで金銭コスト$0）。不満は「時間」と「トークン消費」
- だが実際に調べると、**争点は金額でも時間でもなく「1クエリ10件」という取得上限**だった。
  そのせいで `strategy/growth_strategy.md` のKPI（UGC件数）が全部「下限値」のまま埋まっている
- このリポジトリの必要量は月2,000〜3,000件程度。API化しても**月$0.15〜0.40**なので、金額は争点にならない
- twitterapi.io のアカウントとAPIキーは取得済み
- **前の環境（信頼モード）では `api.twitterapi.io` も `docs.twitterapi.io` も 403 で到達できなかった。
  それがこの環境に移した理由。まず疎通を確認してほしい**

## APIキーの渡し方

**キーをチャットに貼らせないこと。** 次のどちらかで渡す。

- 環境変数 `TWITTERAPI_IO_KEY`（環境設定で登録済みならこれで通る）
- リポジトリのルートの `.env` に `TWITTERAPI_IO_KEY=...` の1行（`.gitignore` 済み）

`work/x_ugc_probe.py` は環境変数を先に見て、無ければ `.env` を読む。
キーが見つからなければエラーで止まるので、まず疎通確認を走らせれば分かる。

## やること（この順で）

### 1. 疎通確認

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://api.twitterapi.io/
curl -s -o /dev/null -w '%{http_code}\n' https://docs.twitterapi.io/
```

403 が返るならこの環境でも届いていない。**その時点で報告して止まること。**
以降の手順は全部ネットワーク前提なので、届かないなら何も進まない。

### 2. エンドポイント仕様の確認（記憶で書かない）

`docs.twitterapi.io/llms.txt` を読んで、次を確定させる。

- 検索エンドポイントのパス（スクリプトの既定は `/twitter/tweet/advanced_search`・**未検証**）
- クエリのパラメータ名（既定 `query`・**未検証**）
- ページングのカーソルのキー名と、次ページ有無の判定方法
- 残高・クレジット照会のエンドポイントがあるか（あれば実残高を確認する）
- 課金単価（引き継ぎ時の想定は $0.15/1,000ツイート、$1 = 100,000クレジット。**要確認**）

**確認済みなのは**ベースURL `https://api.twitterapi.io`、認証ヘッダ `x-api-key`、
`/twitter/user/info?userName=` の3つだけ（ダッシュボードのcURL例で確認）。それ以外は未検証。

ドキュメントと違っていたら `work/x_ugc_probe.py` を直す。既定値を変えるか、
`--search-path` / `--query-param` で上書きできるようにしてある。

### 3. 疎通＋データ品質の確認（1コール・$0.0002程度）

```bash
python3 work/x_ugc_probe.py \
  --check-user lollipop_1116 \
  --query 'from:lollipop_1116 since:2026-08-30 until:2026-09-02' \
  --max-tweets 20
```

返ってきたフォロワー数を `strategy/metrics_2026-09-01.md` の **1,385** と突き合わせる。
一致すればGrokの数値は信用できる。大きく違えばそれ自体が報告すべき発見。

### 4. 本題の検証（最大400件・約$0.06・2分弱）

`strategy_metrics.md` の計測3-1 と同じクエリを**全件列挙**して件数を数える。

```bash
python3 work/x_ugc_probe.py --max-tweets 400 --query \
'("ろりぽっぷ" OR "ろりぽ" OR @lollipop_1116) -from:lollipop_1116 -from:kurumi_lpop -from:mayu_lpop -from:mau_lpop -from:ami_lpop -from:mana_lpop since:2026-08-02 until:2026-09-02'
```

### 5. 結果の報告

| 総件数 | 意味 | 次 |
| --- | --- | --- |
| 20〜30件 | Grokの「下限20件」はほぼ実数。10件の壁は実害なし | **現状維持で確定。**検証終了 |
| 100件以上 | KPIベースラインが実態より大幅に低い | 併用案（案B）に進む価値あり |

生の件数にはノイズ（レンタルサーバー「ロリポップ!」、ゲーム「ロリポップチェーンソー」、菓子）が
混ざっている。100件を超えたら `work/probe_raw.jsonl` を見て**何割がノイズかも報告する**。
そこが案Bで自前で書くことになる部分の重さの目安になる。

実際に消費したクレジットをダッシュボードの残高と突き合わせ、**想定単価が正しかったかも報告**する。

## 判断のルール（守ること）

- **判断はオーナーがする。あなたは材料を出すところまで。**
  「移行すべきです」と結論を先に出さない
- **現状維持を対等な選択肢として扱う。** 非効率を許容してでも$0を選ぶ可能性がある
- 常に**スコープを削って無料枠に収める代案**を併記する（期間短縮、対象の絞り込み、サンプリング）
- 検証結果が「現状維持で確定」なら、**そこで終わり。** 実装に進まない

## 禁止事項（例外なし）

- **$99/月の自動チャージサブスクリプションに登録しない・提案しない**
- 自動チャージ設定を有効にしない
- **明示的な承認なしにクレジットを購入する手順を実行しない**
- **会話ループの中で直接APIを叩かない。** 必ずスクリプト経由で、実行は明示的に
- `--max-tweets` を持たない収集スクリプトを書かない
- APIキーをコードに直書きしない。`.env` か環境変数から読む
- エンドポイント名やパラメータを記憶で書かない。必ずドキュメントを見る
- **並列化しない。** 未課金は 0.2 QPS（5秒/コール）。並列は 429 を誘発するだけ

## 再検討しなくていいこと（結論済み・蒸し返さない）

- **プロバイダは twitterapi.io で確定。** SocialData.tools との差はSDKの有無程度
- **Grok API・Sorsa・GetXAPI・Apify・公式X API はいずれも不採用。**
  理由は調査済み。無料枠の大きさ（Sorsa）や安さ（GetXAPI）を理由に再提案しない
- **Xの全アーカイブDLは使えない。** 収集対象は他人のアカウント（公式＋メンバー7）と
  不特定多数のファン投稿であって、自分のアカウントではない

## 規約・法務

サードパーティ経由の取得はXの規約との関係がグレー。**個人の分析・研究の範囲**を前提とする。
収集した投稿は他人の著作物。手元での分析は通常問題にならないが、再配布・データセット公開・
生成モデルの学習利用は別問題。オーナーがこれを超える用途を指示したら、実装前に一度指摘すること。

生JSON（`work/*.jsonl`）は `.gitignore` 済み。**他人の投稿をリポジトリにコミットしない。**
